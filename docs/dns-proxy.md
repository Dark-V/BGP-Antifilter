# DNS-прокси

Прокси добавляет IPv4-адреса в BGP по DNS-запросам устройств. Это позволяет подхватывать меняющиеся адреса CDN, не дожидаясь следующего обновления списков. По умолчанию прокси выключен.

Клиент запрашивает домен → прокси получает ответ указанного DNS-сервера → применяет include/exclude → передаёт изменения в BIRD → возвращает DNS-ответ. Момент ответа зависит от выбранного режима ожидания.

## Включение

В панели откройте **Настройки → DNS-прокси**:

1. Укажите IP вышестоящего DNS-сервера и порт. Он не должен указывать обратно на этот прокси.
2. Укажите существующий IP сервера для прослушивания и разрешённые сети клиентов. По умолчанию слушатель привязан к `127.0.0.1`. Loopback и собственный адрес слушателя разрешаются автоматически для локальной проверки готовности; доступ остальных клиентов задаётся списком сетей.
3. Выберите режим ожидания, включите прокси, сохраните настройки и перезапустите контейнер. Сохранённые настройки DNS вступают в силу после перезапуска.
4. Настройте устройства на использование этого DNS. Нужен доступ к UDP и TCP на выбранном порту; порт не должен быть занят другим DNS-сервисом.

Прокси работает внутри существующего контейнера. Его внутренний BGP-сеанс использует loopback и порт `DNS_BGP_PORT`; права на изменение маршрутов Linux не требуются. Готовность и число динамических маршрутов видны в панели.

Для проверки готовности используется `DNS_HEALTH_DOMAIN` — по умолчанию `example.org`. Этот домен должен возвращать IPv4-адрес через настроенный DNS-сервер. Проверка проходит через оба слушателя, UDP и TCP, и проверяет соединение с BIRD. `NXDOMAIN`, пустой ответ или ошибка BIRD делают прокси неготовым; причина видна в панели и выводе healthcheck. Панель показывает результат последней проверки готовности.

Настройки можно передать через переменные окружения из `.env.example`. `DNS_RESOLVERS` относится к плановой генерации списков, а `DNS_PROXY_UPSTREAM` — к запросам устройств. Пустой `DNS_RESOLVERS` сохраняет системный DNS генератора; включённому прокси нужен явно заданный upstream.

## Правила

Используются существующие списки **Домены для добавления** и **Домены для исключения**. Одна строка — одно правило:

| Запись | Что подходит |
| --- | --- |
| `forge.com` | Сам домен и все его поддомены |
| `*.forge.com` | Поддомены любой глубины, без самого `forge.com` |
| `video-weaver.*.hls.ttvnw.net` | Например, `video-weaver.eu.hls.ttvnw.net`; `*` внутри имени заменяет ровно одну метку между точками |
| `regex:(^|\.)googlevideo\.com$` | `googlevideo.com` и его поддомены |
| `regex:^scam[0-9]+\.example\.ru$` | `scam1.example.ru`, `scam2.example.ru` и другие имена с цифрами |

Например, include:

```text
*.google.com
regex:(^|\.)googlevideo\.com$
scam1.example.ru
*.forge.com
```

Exclude:

```text
mail.google.com
scam2.example.ru
```

**Исключение всегда имеет приоритет.** `mail.google.com` останется исключённым при наличии `*.google.com` в include. Если включённый и исключённый домены используют один IP, этот IP исключается целиком: BGP различает адреса, а не имена сайтов. Если адрес входит в более крупный маршрут из статического списка, прокси вычитает его из этого маршрута на срок действия исключения.

В разделе **Проверить IP / домен** показаны сработавшее правило и маршруты для адресов домена. При включённом прокси проверяются применённые правила, при выключенном — сохранённые ручные списки. Проверка не меняет правила. После сохранения примените списки обычным обновлением маршрутов; перезапуск для правил не нужен.

Обычные домены по-прежнему разрешаются при плановом обновлении. Маски и regex работают только с наблюдаемыми DNS-запросами и требуют включённого прокси. Такие записи также поддерживаются в загружаемых списках доменов. Для полностью динамического набора можно оставить только маски/regex и отключить статические источники.

В маске `*` занимает целую метку: `api.*.example.com` подходит для `api.eu.example.com`, но не для `api.eu.west.example.com` или `api.eu.example.com.other.test`. Если в маске несколько `*`, каждая заменяет одну метку. Единственная маска в начале, `*.example.com`, по-прежнему охватывает поддомены любой глубины.

Regex применяется к имени без завершающей точки, без учёта регистра; международные имена сначала преобразуются в punycode. Используется поиск совпадения, поэтому для строгих границ нужны `^` и `$`. Длина выражения ограничена 1024 символами, суммарное время проверки regex одного списка — 5 мс. Ошибка или превышение времени не считаются отсутствием совпадения.

## Когда отдавать DNS-ответ

| Режим | Условие ответа |
| --- | --- |
| `async` — по умолчанию | Ответ сразу, маршруты обрабатываются в фоне |
| `bgp` | Наблюдение сохранено, изменения отправлены в локальный BGP-сеанс |
| `bird` | BIRD обработал изменения; наличие или отсутствие маршрута проверено в его таблице |

В режимах `bgp` и `bird` ожидание ограничено `DNS_SYNC_TIMEOUT` — по умолчанию 1 секунда. При сбое или превышении времени `DNS_SYNC_ON_TIMEOUT=servfail` возвращает временную DNS-ошибку без адресов. Значение `forward` отдаёт полученный DNS-ответ, даже если маршрут ещё не подтверждён.

При `HEALTHCHECK_REQUIRE_BGP=1` режим `bird` дополнительно проверяет установленный сеанс с BGP peer. Подтверждение BIRD не означает, что удалённый маршрутизатор уже установил маршрут в свою таблицу пересылки. В `async` и при `forward` первое соединение может начаться раньше появления маршрута.

## TTL и восстановление

Учитываются A-записи, цепочки CNAME, цели HTTPS/SVCB и `ipv4hint` в ServiceMode. Несвязанные дополнительные записи не добавляются. AAAA и остальные DNS-записи передаются клиенту; DNS-транспорт и ACL поддерживают IPv4/IPv6, но BGP-маршруты этой версии остаются IPv4.

Срок адреса берётся из его DNS-записи с запасом `DNS_ROUTE_GRACE` — по умолчанию 30 секунд. Если адрес ещё нужен другому действующему домену, он сохраняется. После истечения последнего срока динамический маршрут снимается; исключение перестаёт действовать по тому же правилу.

Наблюдения хранятся в SQLite в томе `generated`. После перезапуска восстанавливаются только неистёкшие записи. Плановое обновление меняет статическую основу и правила, затем заново применяет к ним действующие наблюдения. Временные адреса не записываются в статический `routes.last-good.conf`.

Прокси видит только запросы, которые проходят через него. Клиентский DoH/DoT или другой DNS обойдут эти правила. При прямой настройке прокси на устройствах ошибка DNS затрагивает их запросы; резервный DNS на роутере сам по себе не обеспечивает им переключение.
