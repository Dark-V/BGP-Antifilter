# AdGuard: маршруты из фактических DNS-ответов

Опциональный DNS-прокси пересылает запросы вашему AdGuard Home и обновляет
IPv4-маршруты в фоне по тому же ответу, который получает клиент. DNS-ответ
по умолчанию отправляется сразу; можно включить ожидание BGP или BIRD. Опрос журнала,
учётная запись AdGuard и SSH не нужны. Настройки самого AdGuard не меняются.

```text
Обычно:  устройства → DNS MikroTik → DNS-прокси → AdGuard
                                    └─ очередь → SQLite → локальный BGP → BIRD → MikroTik
Авария:  устройства → DNS MikroTik ─────────────→ AdGuard
```

## Запуск

Требуется Linux-хост с Docker Compose v2. `BIRD_IP` должен принадлежать
этому хосту и отличаться от адреса AdGuard; порт 53 TCP/UDP на нём должен
быть свободен. В `.env` вместе с обычными настройками BGP задайте:

```dotenv
DNS_PROXY_ENABLED=1
COMPOSE_PROFILES=dns
ADGUARD_DNS=192.168.88.16
UPDATER_COMPOSE_SERVICES=bird admin dns-proxy
```

Прокси слушает `BIRD_IP:53`; проверка готовности доступна на
`http://BIRD_IP:8053/ready`. Разрешённый клиент по умолчанию — только `MT_IP`
и сам хост. Если LAN-адрес MikroTik отличается от BGP-адреса, задайте
`DNS_PROXY_ALLOWED_CLIENTS=192.168.88.1/32` с вашим адресом.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DNS_PROXY_BIND` | `BIRD_IP` | Конкретный локальный IPv4 для DNS и HTTP |
| `DNS_PROXY_ALLOWED_CLIENTS` | `MT_IP/32` | Разрешённые CIDR через запятую |
| `DNS_PROXY_PORT` | `53` | DNS TCP/UDP; для скрипта MikroTik оставьте 53 |
| `DNS_PROXY_HEALTH_PORT` | `8053` | HTTP-порт проверки |
| `ADGUARD_DNS_PORT` | `53` | Порт upstream AdGuard |
| `DNS_ROUTE_GRACE` | `30` | Дополнительное время хранения IP после TTL, секунд |
| `DNS_BGP_PORT` | `1179` | Локальный BGP-вход BIRD, только `127.0.0.1` |
| `DNS_SYNC_MODE` | `async` | Когда возвращать DNS: `async`, `bgp`, `bird` |
| `DNS_SYNC_TIMEOUT` | `1` | Общий срок синхронизации после ответа AdGuard, секунды: больше 0 и до 10 |
| `DNS_SYNC_ON_TIMEOUT` | `servfail` | При таймауте, ошибке или перегрузке: `servfail` либо `forward`; применяется в `bgp`/`bird` |
| `DNS_HEALTH_DOMAIN` | `example.org` | Домен проверки; AdGuard должен разрешать его |

```sh
docker compose up -d --build
docker compose logs -f dns-proxy
curl --fail http://YOUR_BIRD_IP:8053/ready
```

Первоначальная генерация передаёт политику фоновому обработчику и создаёт
`generated/dns-policy.json`. До загрузки политики, соединения локального
BGP и запуска BIRD проверка возвращает 503. Если интеграция включена на
существующем snapshot, дождитесь фонового обновления и ответа 200.

В DNS-режиме BIRD получает маршруты через `dns_live`, локальную iBGP-сессию
с `127.0.0.2` на `127.0.0.1:1179`. Контейнеры не получают `NET_ADMIN`, таблицы
маршрутизации Linux не меняются. `MY_AS` и `DNS_BGP_PORT` должны совпадать
у сервисов `bird` и `dns-proxy`; Compose передаёт их обоим. Пользовательский
шаблон BIRD должен поддерживать `${ROUTE_SOURCE_PROTOCOL}`, как штатный.

## Ожидание маршрутов перед DNS-ответом

| Режим | Порядок обработки | Что подтверждено перед ответом |
| --- | --- | --- |
| `async` | Ответ → фоновое сохранение → BGP | Обновление маршрута ещё может идти |
| `bgp` | Сохранение → отправка локального BGP UPDATE → ответ | Изменения отправлены в сокет BIRD; приём/применение не подтверждены |
| `bird` | Сохранение → BGP → подтверждение BIRD → ответ | BIRD обработал изменения и его выбранный маршрут для каждого IP соответствует политике |

Например, чтобы дождаться локального применения правил:

```dotenv
DNS_SYNC_MODE=bird
DNS_SYNC_TIMEOUT=1
DNS_SYNC_ON_TIMEOUT=servfail
```

Примените настройки через `docker compose up -d --build`. Ожидание относится к
конкретному ответу, а не к опустошению всей очереди. Запросы других клиентов
продолжают обрабатываться. Домены вне списков и известных связей CNAME/SVCB
не ждут BGP/BIRD; их принадлежность проверяет фоновый обработчик. Ожидание
для выбранных доменов охватывает и включения, и исключения, включая общий IP.
Записи и связи псевдонимов сохраняются до ответа в режимах `bgp`/`bird`.
Их срок хранения дополнительно продлевается на `DNS_SYNC_TIMEOUT`, чтобы
ожидание ответа не съело часть TTL, который затем отсчитывает клиент.

```text
AdGuard вернул новый IP
        → SQLite → точечный BGP UPDATE → BIRD обработал UPDATE → проверка IP
                                                                     → DNS-ответ
        └─ общий таймаут/ошибка/полная очередь
             servfail → SERVFAIL без IP; клиент может повторить запрос
             forward  → исходный ответ AdGuard; гонка маршрутов допустима
```

Таймаут общий для очереди, сохранения, отправки и проверки BIRD. Он не включает
ожидание самого AdGuard. Ответ после неудачного ожидания всё равно учитывается
в фоне, если попал в очередь. Для контроля обработки BIRD используется служебный
префикс `198.18.0.1/32` с меткой процесса и номером изменений: он защищён
`NO_ADVERTISE` и явно запрещён экспортным фильтром. Это позволяет подтвердить
обработку удалений, а не принять преждевременное отсутствие маршрута за успех.
Префикс зарезервирован в режиме `bird`; при своём шаблоне сохраните запрещающий
его экспорт фильтр из штатного `bird.conf.template`.

`bird` подтверждает **локальную таблицу BIRD**, а не установку маршрута в
MikroTik. При `HEALTHCHECK_REQUIRE_BGP=1` дополнительно требуется состояние
`Established` внешней сессии, но это тоже не подтверждение таблицы MikroTik.
Автоматический прямой режим MikroTik продолжает обходить прокси: ожидание
на нём не применяется. IPv6 эта интеграция по-прежнему не маршрутизирует.

## MikroTik: автоматическое переключение

Устройства используют LAN-адрес MikroTik как DNS. Его DNS-сервис должен
принимать запросы из LAN (`allow-remote-requests=yes` и ваши обычные правила
firewall). DHCP, firewall и AdGuard скрипт не меняет.

Сгенерируйте `.rsc` для **фактического адреса** хоста с прокси:

```sh
python3 scripts/mikrotik-dns-failover.py \
  --proxy YOUR_BIRD_IP --direct 192.168.88.16 \
  --output generated/mikrotik-dns-failover.rsc
```

Загрузите файл через Files. Перед импортом сохраните текущую конфигурацию
командой `/export file=before-bgp-dns`. Затем:

```routeros
/import file-name=mikrotik-dns-failover.rsc
```

Скрипт для RouterOS 7 сразу устанавливает прямой DNS `192.168.88.16` и
создаёт два script и два scheduler с именами `bgp-dns-*`. Каждые 5 секунд:

- 3 успешные проверки подряд → единственный upstream меняется на прокси;
- 2 неудачные подряд → единственный upstream меняется на AdGuard;
- после перезагрузки → прямой режим до успешных проверок;
- при переходе очищается DNS-кеш MikroTik; стабильное состояние не вызывает
  записи настроек и сообщений в лог.

`/ready` проверяет оба реальных DNS-входа (UDP и TCP), прохождение запроса
через AdGuard, работоспособность фонового обработчика и локальной BGP-сессии,
состояние BIRD и, при
`HEALTHCHECK_REQUIRE_BGP=1`, состояние BGP Established. Проверка выполняется
через Scheduler с нужными правами; проверка прав не отключается.

Просмотр и ручное включение прямого режима:

```routeros
/ip dns print
/system scheduler print where name~"bgp-dns"
/log print where message~"BGP DNS"
/system scheduler disable [find where name="bgp-dns-watch"]
/system script run bgp-dns-direct
```

Для удаления сначала включите прямой режим командами выше, удалите два
scheduler и два script `bgp-dns-*`, установите `DNS_PROXY_ENABLED=0`, очистите
`COMPOSE_PROFILES`, верните `UPDATER_COMPOSE_SERVICES=bird admin` и выполните
`docker compose up -d --build --remove-orphans`. При необходимости верните
свои прежние настройки DNS из экспорта.

## Обработка маршрутов

- У прокси нет своего DNS-кеша. Кеширование остаётся у AdGuard, MikroTik
  и клиентов; записи и DNSSEC-данные upstream передаются клиенту.
- Маршруты добавляются для `include-domains.txt`, доменов из
  `domain-list-urls.txt` и их поддоменов. Остальные запросы пересылаются.
  CNAME-цепочки и IPv4-подсказки HTTPS/SVCB учитываются.
  Если клиент запрашивает адрес псевдонима отдельно, его связь с исходным
  доменом сохраняется с TTL и восстанавливается после перезапуска.
- `exclude-domains.txt` и его поддомены имеют приоритет: адрес из ответа
  исключается даже из более крупного префикса. Статические исключения также
  имеют приоритет над новыми включениями.
- Если клиенты получили IP1 и IP2, сохраняются оба до TTL каждого ответа
  плюс `DNS_ROUTE_GRACE`. Повторный ответ продлевает срок и не запускает
  скачивание списков. Неглобальные IPv4, включая `0.0.0.0` и частные адреса,
  не превращаются в маршруты.
  Время хранения IP определяется TTL его A-записи или HTTPS/SVCB-подсказки:
  короткий TTL промежуточного CNAME не сокращает срок хранения адреса.
- По умолчанию (`async`) ответ AdGuard передаётся сразу. Новые IPv4 обрабатываются в ограниченной
  фоновой очереди; данные сохраняются в SQLite, затем объявляются отдельными
  BGP UPDATE. Для обычного добавления/удаления IP нет полного обхода маршрутов,
  перезаписи `routes.conf` и `birdc configure`. Исключение внутри подсети меняет
  только покрывающий префикс и до 32 его частей.
- При первом ответе клиент может подключиться до доставки BGP-обновления
  в MikroTik. Это относится к асинхронному режиму. Ошибка маршрутов или заполненная
  очередь не заменяет корректный DNS-ответ на SERVFAIL: `/ready` возвращает 503,
  чтобы MikroTik мог перейти в прямой режим. Ошибка самого upstream DNS
  по-прежнему приводит к SERVFAIL.
- Очередь ограничена 1024 событиями и 16384 адресами/связями. Пакеты событий
  обрабатываются каждые 20 мс, повторные изменения одного префикса объединяются.
  Превышение лимита отражается в readiness; это не ограничитель DNS QPS.
- Полный индекс строится при запуске и обновлении исходных списков. Новая
  политика объединяется с ещё действующими наблюдёнными IP; они входят в
  snapshot и остаются объявленными. При разрыве локального BGP желаемая таблица
  сохраняется в памяти и полностью отправляется после восстановления; BIRD
  поддерживает graceful restart этого источника до 120 секунд.
- Проект объявляет IPv4. AAAA и остальные записи передаются, но
  IPv6-маршруты эта интеграция не создаёт.
- При прямом режиме DNS работает через AdGuard; наблюдение новых ответов
  возобновляется после возврата на прокси.

Активные правила: `generated/dns-policy.json`. TTL-записи и связи псевдонимов
хранятся в `generated/dns-cache.sqlite3` (SQLite WAL); JSON-файлы предыдущей
реализации импортируются при первом запуске. `routes.conf` и
`routes.last-good.conf` — snapshots полного обновления, а актуальная живая
таблица находится в BIRD (`birdc show route protocol dns_live`). Плановое
обновление не теряет активные записи из SQLite. Не удаляйте файлы SQLite WAL
и SHM у запущенного сервиса. `dns-worker.lock` защищает от второго обработчика;
`dns-apply.lock` сериализует запросы полного обновления и снимается ОС при
завершении процесса. `status.json` описывает последнюю полную генерацию.

## Проверка после установки

1. Запросите включённый домен через MikroTik; проверьте полученный IP:
   `docker compose exec bird birdc show route for RECEIVED_IP`.
2. `docker compose stop dns-proxy`: после двух неудачных проверок DNS
   MikroTik должен стать `192.168.88.16`, резолвинг должен продолжаться.
3. `docker compose start dns-proxy`: после трёх успешных проверок DNS
   должен вернуться на прокси.

Разработчикам: `python3 -m pip install -r requirements.txt`, затем
`python3 -m unittest discover -s tests`. Linux Docker smoke test проверяет
UDP/TCP, точечные объявления/удаления в настоящем BIRD без `configure`,
сохранение IP после полной генерации, отдельный запрос псевдонима после
перезапуска, 503 readiness и работающий DNS при остановленном BIRD.
Импорт и переключение на
физическом MikroTik проверяются отдельно.
